# Neurology Branching Tree — Master Build Plan
**Target: Flutter (web + APK), local-first, zero cloud cost**

> Paste this whole document into AntiGravity as the project spec. Work through phases in order — do not skip to UI before Phase 2 (guardrails) is working, or you will build a pretty UI on top of an unverified engine.

---

## 0. Non-negotiable laws (from project spec — do not let the AI coding agent violate these)

1. **Probability Trap Guardrail**: Probability is ALWAYS computed by a deterministic formula (Section 4). Never let an LLM output a probability number directly. Vague/single symptom → probability must be mathematically forced low (1-5%), never inflated.
2. **Anti-Hallucination Law**: If a symptom combination has no matching node in the local DB, the app must return `NO_VERIFIED_DATA`, full stop. No LLM-generated fallback text, ever.
3. **Local LLM (Qwen3 8B via Ollama) does exactly one job**: natural language → JSON array of symptom tags from a *fixed, closed vocabulary*. It never writes advice, never writes probabilities, never free-texts.
4. This dataset is a **proof-of-concept** covering ~12 well-known neurology conditions. It is explicitly NOT clinically validated and must be reviewed by a medical professional before any real-world use. Every disease node carries a `"source"` and `"clinical_review_status": "unreviewed"` field for this reason.

## 1. Tech stack

| Layer | Choice | Why |
|---|---|---|
| App framework | **Flutter (Dart)** | Single codebase → Web build + Android APK |
| State mgmt | `flutter_riverpod` | Clean, testable, good for async loading states |
| Local LLM runtime | **Ollama**, model `qwen3:8b` | Runs locally, zero API cost, structured JSON output support |
| Parser constraint | Ollama's structured output (JSON schema / grammar) via `format: json` + Pydantic-style validation | Forces closed-vocabulary output — this is your real anti-hallucination enforcement point |
| Vector search | **TurboVec** (or if unavailable, `sqlite-vec` / simple cosine similarity over a small local embedding set — see note in Phase 3) | Symptom string matching, <100MB footprint |
| Local backend | **FastAPI** (Python), running on `localhost:8008` | Bridges Flutter app ↔ Ollama ↔ SQLite/TurboVec. Flutter never talks to Ollama directly. |
| Database | **SQLite** (file-based, bundled with app or in app documents dir) | Diseases → Variants → Symptoms → Treatments, flat and inspectable |
| Data format | JSON (source of truth) → compiled into SQLite at build/setup time | Easy to hand-edit and version in git |

**Architecture flow:**
```
Flutter App (Web/APK)
      |
      v
FastAPI local server (localhost:8008)
      |
      +--> Ollama (qwen3:8b) -- text -> JSON symptom tags ONLY
      |
      +--> TurboVec / similarity search -- symptom tags -> candidate disease nodes
      |
      +--> SQLite -- candidate nodes -> full disease/variant/treatment data
      |
      +--> Deterministic scoring engine -- nodes + symptoms -> probability %
      |
      v
JSON response -> Flutter renders cascading cards
```

## 3. Phased build plan (work through in this order)

### Phase 1 — Data layer first (no code yet)
1. Finalize `symptom_vocabulary.json` — closed list of every symptom tag the system will ever recognize (e.g. `resting_tremor`, `loss_of_balance`, `unilateral_weakness`). This is the vocabulary Qwen3 is constrained to output from.
2. Finalize `neurology_dataset.json` using the starter dataset provided separately (see `01_STARTER_DATASET.json`). Each disease node must have: `id`, `name_clinical`, `name_plain`, `variants[]`, `pathognomonic_symptoms[]` (defining/near-certain indicators), `supporting_symptoms[]` (common but non-specific), `treatments[]`, `source`, `clinical_review_status`.
3. Write `data/build_db.py` to compile the JSON into SQLite. This is a pure, deterministic script — no AI involved.
4. **Test**: manually inspect the SQLite output. This is your ground truth; get it right before anything else touches it.

### Phase 2 — Deterministic scoring engine (build & test BEFORE the LLM parser)
1. Implement the weighted scoring formula in `scoring_engine.py` (full formula given in Section 4 below).
2. Write unit tests FIRST: given a fixed symptom list, assert the exact expected probability. E.g. `["headache"]` alone against Migraine → must assert `<= 5%`. `["resting_tremor", "bradykinesia", "rigidity"]` → must assert high probability, since these are pathognomonic for Parkinson's.
3. This engine takes **only structured symptom tags** as input — never touches the LLM output directly, so you can fully unit-test it in isolation before Ollama is even wired up.

### Phase 3 — Search layer
1. Wire up `search_service.py`. If TurboVec proves hard to set up locally, start with a much simpler approach: precompute embeddings for each `symptom_vocabulary.json` entry using a small local model (or even just exact-match + synonym table for v1 — this is legitimate for a closed vocabulary and much easier to debug). Swap in TurboVec later once the core pipeline works.
2. **Test**: given a symptom tag array, confirm it returns the correct candidate disease node IDs from SQLite.

### Phase 4 — LLM parser (last, because it's the least deterministic piece)
1. Set up Ollama locally, pull `qwen3:8b`.
2. Write `parser_service.py`: strict system prompt forcing output to be *only* a JSON array drawn from `symptom_vocabulary.json`. Use Ollama's `format: json` mode plus post-validation in Python (reject/retry if any tag isn't in the closed vocabulary — never silently pass through an invented tag).
3. **Test**: feed it 10-15 varied natural-language descriptions, confirm outputs are always valid closed-vocabulary JSON, confirm it never adds commentary or advice text.

### Phase 5 — FastAPI orchestration
1. `main.py` wires parser → search → DB fetch → scoring engine → response JSON.
2. Implement the `NO_VERIFIED_DATA` fallback explicitly: if search returns zero candidates above a minimum symptom-overlap threshold, return that flag — never let the DB layer "guess" a closest match and present it as real.
3. **Test**: end-to-end with a nonsense input (e.g. "my elbow itches") — confirm it correctly returns `NO_VERIFIED_DATA`, not a hallucinated neuro condition.

### Phase 6 — Flutter frontend
1. Input screen (Screen 1): minimal search field.
2. Skeleton shimmer + processing log (Section 5 details).
3. Tree screen (Screen 2): cascading expandable cards, probability badges, variant/treatment drill-down.
4. Wire `api_client.dart` to the FastAPI backend.
5. Build web target (`flutter build web`) and APK target (`flutter build apk`) — confirm both work off the same codebase.

### Phase 7 — Integration testing & review
1. Full pipeline test with realistic phrasing.
2. **Mandatory**: flag every disease node's `clinical_review_status` prominently in the UI itself (not just internally) until a clinician has reviewed the dataset.

## 4. The deterministic scoring formula

Use a weighted symptom-match score, NOT an LLM-estimated probability.

```
For a given disease node D with:
  P = set of pathognomonic (defining) symptoms for D
  S = set of supporting (non-specific) symptoms for D
  U = set of symptoms extracted from the user's input

  pathognomonic_matches = |P ∩ U|
  supporting_matches     = |S ∩ U|

  pathognomonic_weight = 15   (points per matched defining symptom)
  supporting_weight    = 3    (points per matched supporting symptom)

  raw_score = (pathognomonic_matches * pathognomonic_weight)
            + (supporting_matches * supporting_weight)

  max_possible_score = (|P| * pathognomonic_weight) + (|S| * supporting_weight)

  confidence_pct = round( (raw_score / max_possible_score) * 100 )

  HARD CAP RULE:
    if pathognomonic_matches == 0:
        confidence_pct = min(confidence_pct, 5)   # vague/non-specific symptoms can never exceed 5%

  if confidence_pct == 0 and supporting_matches > 0:
        confidence_pct = 1   # floor, so it's not literally zero when there's SOME overlap
```

This guarantees: a single vague symptom like "headache" (which is only a *supporting* symptom for nearly everything) can never mathematically produce a high score, because it hits the hard cap. Only genuine pathognomonic combinations can push the score up. This is exactly your Probability Trap Guardrail, implemented as math, not vibes.

## 5. UI states (for the Flutter build)

**Loading sequence** (~2-4 sec while backend processes):
1. Instant: render skeleton shimmer cards (blank pulsing placeholders in the shape of the eventual disease cards).
2. Inline text ticks through: `[Step 1/3: Dissecting language...]` → `[Step 2/3: Searching Neurology Index...]` → `[Step 3/3: Calculating probability...]` — these are just tied to your actual backend call stages, not decorative.

**Result screen**:
- Each disease = collapsed card showing name (plain-language), probability badge.
- Tap to expand → shows variants, pathognomonic vs supporting symptoms (matched ones highlighted), treatments.
- If `NO_VERIFIED_DATA`: render a distinct, honest empty-state card — "No verified clinical data available for this combination" — never silently show nothing or a generic disclaimer.
- Every card footer: small persistent note "Unreviewed dataset — for architecture demonstration only" until clinical review is done.
